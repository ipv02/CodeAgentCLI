# Ассистент поддержки пользователей

## Назначение

`agent --support-chat --support-ticket ID` запускает отдельный интерактивный
режим, который отвечает по документации продукта и учитывает состояние
конкретного обращения. Режим не меняет обычный чат, контекстный чат или индекс
Pipeline MCP.

## Поток данных

1. На каждом пользовательском вопросе `SupportAssistantService` вызывает
   read-only MCP tool `get_ticket_context`.
2. MCP-сервер читает JSON, проверяет связи тикета и пользователя и возвращает
   только разрешённые поля.
3. Вопрос дополняется категорией, темой, кодом ошибки и состоянием аккаунта для
   поиска по отдельному индексу FAQ.
4. В модель передаются ограниченные блоки `TICKET_CONTEXT` и
   `PRODUCT_EVIDENCE`. Оба блока считаются недоверенными данными.
5. Источники и цитаты строятся детерминированно из найденных chunks. При слабом
   контексте генерация не вызывается, а тикет направляется на эскалацию.

В историю текущего обращения записываются только чистый вопрос и итоговый
ответ. Сырые MCP-данные и Evidence не становятся памятью задачи или профилем.

## JSON-контракт

Корневой объект содержит массивы `users` и `tickets`. Идентификаторы уникальны,
а каждый `ticket.user_id` должен ссылаться на существующего пользователя.

Разрешённые поля пользователя:

- `id`, `plan`, `account_status`;
- `auth_provider`, `mfa_enabled`, `locale`;
- `last_successful_login_at`.

Разрешённые поля тикета:

- `id`, `user_id`, `status`, `priority`, `category`;
- `subject`, `description`, `created_at`;
- `diagnostics.error_code`, `failed_attempts`, `password_changed_at`, `client`.

Все остальные поля, включая контактные данные и произвольные диагностические
значения, отбрасываются на границе MCP.

## MCP tools

- `get_user(user_id)` — безопасный контекст аккаунта;
- `get_ticket(ticket_id)` — данные одного тикета;
- `get_ticket_context(ticket_id)` — тикет вместе со связанным пользователем.

Встроенный сервер можно добавить в постоянный config командой
`/mcp init-support`. Режим поддержки использует сервер `support-data` из этого
config, а если он не зарегистрирован — запускает встроенный provider. Поэтому
для подключения реальной CRM можно заменить сервер `support-data`, сохранив
контракт `get_ticket_context`.

## Индекс и конфигурация

По умолчанию используются:

- данные: `code_agent_cli/support_data/support.json`;
- FAQ: `code_agent_cli/support_data/faq.md`;
- индекс: `~/.code-agent-cli/support/document_index.db`;
- история: `~/.code-agent-cli/support/history.json`.

Переопределения:

- `CODE_AGENT_SUPPORT_DATA_FILE`;
- `CODE_AGENT_SUPPORT_DOCS`;
- `CODE_AGENT_SUPPORT_DIR`;
- `CODE_AGENT_SUPPORT_INDEX_DB`.

Для реальной CRM достаточно зарегистрировать совместимый `support-data` provider
с тем же нормализованным результатом. Оркестратор ответа и RAG-слой при этом не
знают транспорт и внутреннюю CRM-схему.

## Проверка

```bash
agent --support-index
agent --support-chat --support-ticket SUP-1001
```

Контрольный вопрос: `Почему не работает авторизация?`. Для `SUP-1001` ожидаются
ссылка на `session_revoked`, рекомендация завершить старую сессию и войти новым
паролем, а также источник и цитата из FAQ.
